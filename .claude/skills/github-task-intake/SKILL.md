# GitHub Issue タスク起票

思いつきをそのまま issue にせず、いくつかの観点で人間と一緒に理解を深めてから起票するスキル。目的は**着手前に曖昧さを削っておくこと**。判断するのは常にユーザーで、Claude は観点を出して考えるのを手伝う役。

**前提**: `gh` CLI がインストール・認証済みであること（`gh auth status`）。リポジトリは `SystemEngineeringTeam/sysken-pay`。

## Step 1: アイデアを聞く

やりたいこと・直したいことを聞く。会話の中で十分語られていれば聞き直さない。

## Step 2: 既存 issue との重複を確認する

`gh issue list --search "<キーワード>" --state all` で似た issue が無いか確認する。あれば、新規起票か既存の更新かをユーザーに確認する。

## Step 3: 観点で理解を深める

儀式的に全部聞くのではなく、会話の中で確認する。関係ない観点は軽く流してよい。ただし**会計観点だけは特別**（後述）。

- **Engineer 観点**: フロント（React / Zustand / generouted）とバック（Go のレイヤー構成: ui → usecase → domain → infra）のどちらに、どこまで手が入るか。API を変えるなら `docs/openapi.yaml` の更新と `pnpm generate:api` が必要。ざっくりの工数感
- **PM 観点**: スコープは適切か（大きすぎるなら分割を提案）。他タスク・他の人の作業との依存はあるか
- **PO 観点**: 受け入れ条件（完了の定義）を明確にできるか。誰（買う部員 / チャージする部員 / 管理者）にどんな価値があるか
- **Designer 観点**（画面に関わる場合）: 800x480 のタッチ画面に収まるか、既存の画面の流れ（左下「戻る」・右下「次へ」等）と一貫しているか。`pi-display-ui` スキルのルールに沿うか
- **会計観点**（お金・残高・購入履歴・チャージに関わるタスク）: 残高が正しく保たれるか

### 特別ルール: 会計観点の懸念は必ず言葉にして解消する

お金に関わる懸念が少しでも浮かんだら、他の観点がすべて問題なくても、**そのまま流さずユーザーに明示し、一緒に解消してから次へ進む**。「実装上は問題ないので起票します」で済ませない。たとえば:

- 二重送信（ボタン連打・通信の再送）で二重に引き落とし・チャージされないか
- 途中で失敗したとき、残高と履歴の片方だけ更新されないか（トランザクション）
- 取消・返金の手段と、その記録が残るか
- 負の金額・極端な金額・残高不足をどこで止めるか
- 現金箱の中身と残高の合計を後から突き合わせられるか

## Step 4: 起票内容をまとめる

- **タイトル**: 番号は付けない。先頭に種類の prefix（`feat:` 新機能、`fix:` 不具合、`docs:` ドキュメント、`chore:` 雑務）。対象が片方だけなら `feat(front):` / `fix(back):` のように書いてもよい。例: `fix(back): 購入APIの二重送信で残高が二重に引かれる`
- **背景・なぜやるか**
- **受け入れ条件（完了の定義）**
- **スコープ**: 含むこと / 含まないこと
- **実装メモ**: Engineer 観点で出た技術的な考慮点（あれば）
- **検討メモ**: 会計観点などで話し合った内容（特に懸念とその解消内容は残す）

## Step 5: 確認する

ドラフトを見せ、「この内容で起票する / 直す / やめる」を確認する（AskUserQuestion が使えれば使う）。直すなら Step 3〜4 に戻る。

## Step 6: issue を作成する

1. `gh label list` で既存ラベルを確認し、合うもの（`frontend` / `backend` / `bug` 等）があれば使う。**無いラベルを勝手に作らない**
2. 本文を Markdown に整形する（見出しは `##` 程度）
3. `gh issue create --title "<タイトル>" --body "<本文>"`（必要なら `--label`）
4. 作成した issue の URL と番号を伝える
