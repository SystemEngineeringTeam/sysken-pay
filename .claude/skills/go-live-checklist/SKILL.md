# Go-Live Checklist

本番運用を始める前に、運用してよい状態かを棚卸しするスキル。目的は止めることではなく、**何が起きうるかをユーザーが理解した上で判断できる状態にする**こと。明らかに危険な状態（秘密情報のコミット、お金を動かす API が誰でも叩ける等）を見つけたら、直るまでデプロイに進まない。

## Step 1: 公開範囲とリスクレベルを判定する

シス研Pay は**部員の学籍番号・氏名と、お金（残高・購入履歴）**を扱う。この時点でリスクは「中」以上になる。

ユーザーに確認する（コードから分かることは聞かない）。

- バックエンド（Go の API、ポート 8080）と MySQL（ポート 53306）に**どこから届くか**: ラズパイの中だけ / 部室・大学の LAN / インターネット
- 実際のお金（現金）と残高が対応しているか、遊び用のポイントか
- 壊れたり漏れたりしたら誰がどう困るか

| レベル | 目安 | 対応 |
|---|---|---|
| **中** | API と DB がラズパイの中（localhost）からしか届かない | Step 2〜3 を全部通し、残るリスクを明示して運用開始 |
| **高** | API や DB が LAN・インターネットから届く、または実際の現金と対応する残高を扱う | Step 2〜3 を通した上で、**運用前に詳しい人（先輩・教員など）のレビューを強く推奨する**。この推奨を省かない |

高リスクのとき「Claude のチェックだけで大丈夫」とは言わない。

## Step 2: コードと設定の棚卸し

実際にコード・設定・履歴を読んで確認する。

**秘密情報**
- `.env` が Git 管理に入っていないか（`git ls-files | grep -i env`）。過去の履歴も確認（`git log --all --diff-filter=A --name-only -- '*.env*'`）。見つかったらキー・パスワードの**変更を先に**案内する
- ハードコードされたパスワード・トークンがないか（`git grep -n -i -E 'password|secret|token'`）
- **`VITE_ADMIN_PASSWORD` はビルド後の JS に埋め込まれる**。ブラウザの開発者ツールやビルド成果物から誰でも読める。キオスク端末に物理的に触れる人・`dist/` を取得できる人には管理パスワードが見えている前提で、許容できるか判断してもらう

**認証・認可（お金を動かす API）**
- チャージ・購入・購入取消・ユーザー登録・商品登録の API（`sysken-pay-backend/app/ui/api/**`）が、認証なしで叩けないか。管理者パスワードがフロントだけで判定されていてバックエンドに認証が無い場合、**API に届く人は誰でも任意の学籍番号にチャージできる**。Step 1 で API が LAN 以上に届くなら「直してから運用すべき」に分類する
- 他人の学籍番号で購入・残高照会ができる作りか（学生証のバーコードだけで本人確認している点を含めて、運用上許容できるかを確認する）

**露出面**
- `docker-compose.yaml` の `ports`: MySQL の `53306` がホストの全インターフェースに公開されていないか。ラズパイ外から届く必要がなければ `127.0.0.1:53306:3306` に絞る提案をする
- バックエンドの `8080` も同様。フロントとバックが同じラズパイなら `127.0.0.1` に絞れる
- CORS が `*` になっていないか
- エラー時にスタックトレースや SQL を返していないか

**データと運用**
- **MySQL のデータがボリュームに保存されているか**。`volumes:` に `mysql_data` が宣言されていても `db` サービスにマウントされていなければ、`docker compose down` でデータが消える。直してから運用する
- バックアップ: `mysqldump` を定期的に取る仕組み（cron 等）と、保存先（ラズパイの SD カード以外）があるか。SD カードは壊れる前提で考える
- 依存の脆弱性: `cd sysken-pay-front && pnpm audit --prod`、`cd sysken-pay-backend && go run golang.org/x/vuln/cmd/govulncheck@latest ./...`
- テスト: `pnpm exec vitest run src/test`、`go test ./...` が通るか
- 壊れたときに前のバージョンへ戻す手段（`safe-rollback` の 4-D）をユーザーが把握しているか
- ラズパイの電源断・再起動で、バックエンド・DB・キオスク表示が自動で立ち上がるか

## Step 3: `/security-review` を実行する

ビルトインの `/security-review` で、反映するブランチの変更をレビューする。Step 2 は構成の棚卸し、こちらはコードの脆弱性（SQL インジェクション、金額計算の不正な値の受け入れ等）を見る層なので、どちらか一方で済ませない。特に金額（負の値・桁あふれ・小数）と在庫・残高の同時更新（トランザクション）を重点的に見てもらう。

## Step 4: 結果を平易な言葉で報告し、判断を仰ぐ

項目ごとに「問題なし / 直してから運用すべき / 運用後でよいが対応推奨」に分けて報告する。

- 「直してから運用すべき」が残っている間はデプロイしない
- すべて通っても「絶対に安全」とは言わない。見ていないもの（ラズパイ自体の OS アカウント・SSH の守り、物理的な盗難、部室ネットワークの他の機器）を一言添える
- 高リスクのときは、詳しい人のレビューの推奨を報告の冒頭に置く
- 運用開始後の最低限として「バックアップが毎日取れているか時々確認する」「おかしいと思ったら `safe-rollback`」の2点を伝える

ユーザーが残リスクを理解した上で「運用する」と決めたら、そこで初めてデプロイ作業に進む。
