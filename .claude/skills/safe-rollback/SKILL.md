# Safe Rollback

壊れた状態から安全に回復するためのスキル。最優先は「元に戻すこと」ではなく「**これ以上悪化させないこと**」。今ある状態は、消さない限り後から調査・回復できる。

シス研Pay は**部員のお金（残高・購入履歴）を扱う**。コードは戻せても、DB のデータを消すと取り返せない。DB に触れる操作は、コードより一段慎重に扱う。

## 大原則

1. **消さない・上書きしない。** 使ってよいのは「追加する」操作（ブランチ作成、stash 退避、revert コミット）だけ。`git reset --hard`、`git clean`、`git checkout -- .`、force push、`docker compose down -v`、`docker volume rm` は使わない（`.claude/settings.json` の deny と hook でもブロックされている）
2. **作業前に必ず退避する。** コードはバックアップブランチ、DB は `mysqldump` で退避してから触る
3. **1操作ごとに平易な言葉で説明する。** 「これから何をするか」「何が起きるか」「失敗してもやり直せるか」を一言ずつ添える
4. **2回試して直らなかったら手を止める。** 現状・試したこと・残りの選択肢を整理して報告する

## Step 1: 現状を凍結して把握する

読み取り系コマンドだけで状況を集める。

```
git status
git log --oneline -15
git diff
git stash list
```

あわせてユーザーに聞く。

- いつまでは動いていたか
- 壊れる直前に何をしたか（コード変更・Claude への依頼・ラズパイへの反映・DB 操作）
- どの画面で、何をしたら、何が起きるか（エラー表示やスクリーンショット）
- **お金に関わる症状か**（残高が合わない、二重に引かれた、チャージが消えた）。そうなら Step 4-E を最優先で読む

## Step 2: どこが壊れているかを切り分ける

| 状況 | 見分け方 | 対応 |
|---|---|---|
| 未コミットの変更で壊れた | `git status` に変更があり、最後のコミットでは動いていた | 4-A |
| コミット済み（未push）で壊れた | 壊した変更がローカルのコミットにある | 4-B |
| push 済みで壊れた | GitHub にも上がっている | 4-C |
| ラズパイの本番が壊れた | 部室の端末で動かない・表示が崩れる | 4-D |
| DB・データがおかしい | 残高や商品が消えた・合わない、`init.sql` を変えた後からおかしい | 4-E |

フロント（`sysken-pay-front`）とバック（`sysken-pay-backend`）のどちらの変更で壊れたかも分ける。`git log --oneline -- sysken-pay-front` / `-- sysken-pay-backend` で範囲を絞れる。

## Step 3: 現状を退避する

```
git stash push -u -m "rollback前の未コミット退避 <日付>"   # 未コミット変更がある場合
git branch backup/before-rollback-<日付>
```

ユーザーには「今の状態は `backup/...` という名前で保存したので、この後何が起きても今の時点には戻れます」と伝える。

## Step 4: 安全な手段で復旧する

### 4-A: 未コミットの変更を取り消す

`git restore` で捨てずに `git stash push -u -m "壊れた変更の退避 <日付>"` で退避する。stash は消さずに残す。

### 4-B: コミット済み（未push）の変更を取り消す

`git reset` ではなく `git revert <コミット>`。複数なら `git revert --no-commit <古い方>..HEAD` してから1コミットにする。

### 4-C: push 済みの変更を取り消す

ローカルで `git revert` して通常の `git push`。PR 運用なので revert も PR で出す。force push はしない。

### 4-D: ラズパイの本番を戻す

コードを直して再デプロイするより、**前に動いていたコミットをラズパイで動かし直す**方が速くて確実。

1. ラズパイで今動いているコミットを確認する（`git log -1`）
2. 動いていたコミットを `git switch -c rollback/<日付> <コミット>` で取り出す（今のブランチは消さない）
3. フロント: `pnpm install && pnpm build` → キオスクのブラウザを再読み込み
4. バック: `docker compose build && docker compose up -d`
   - **`docker compose down` は使わない**。今の `docker-compose.yaml` は MySQL のデータをボリュームに保存していないので、コンテナを消すと残高データが消える（4-E 参照）。`up -d` はコンテナを作り直さずに済む場合が多いが、DB コンテナが作り直される変更（`db` サービスの設定変更）が含まれていないかを先に `git diff` で確認する

### 4-E: DB・データを戻す

ここは慎重さを一段上げる。間違った巻き戻しでデータを失うと回復できない。

1. **何よりも先に今の DB を退避する**:
   `docker exec sysken-db mysqldump -u root -p sysken_pay > backup-<日付>.sql`
   （パスワードはユーザーに入力してもらう。Claude は `.env` を読まない）
2. 退避が取れたことをファイルサイズと先頭行で確認してから次へ進む
3. 戻す手段（以前の dump、手での修正 SQL）があるかを確認する。**どちらも無い、または削除・上書きを伴う場合は実行せずに手を止め**、状況を整理してユーザーに判断を仰ぐ
4. 残高のずれは、`balance` を直接書き換えず、購入・チャージの履歴と突き合わせて原因の取引を特定する。直すときは、どの行を・なぜ・どう変えるかを示して明示的な承認を得る
5. `init.sql` は**最初にコンテナを作るときだけ**実行される。`init.sql` を書き換えても既存 DB は変わらない。スキーマを変えたいときに DB を作り直す（= データを消す）方向へ進まない

## Step 5: 直ったことを確認する

- フロント: `cd sysken-pay-front && pnpm build && pnpm exec vitest run src/test`
- バック: `cd sysken-pay-backend && go test ./...`
- 訴えのあった症状が実際に消えたかを、可能ならユーザー自身に部室の端末で見てもらう

## Step 6: 平易な言葉でまとめる

- 何が原因だったか（分からなければ「分からなかった」）
- 何をどこまで戻したか
- 退避した状態がどこに残っているか（`backup/...` ブランチ、stash、DB の dump ファイル）
- 再発防止に次にやるとよいこと

退避ブランチ・stash・dump は勝手に消さない。ユーザーが「もう要らない」と言ったときだけ片付ける。
