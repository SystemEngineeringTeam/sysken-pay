# 管理サイトの Entra ID ログインの設計

PC の管理サイト（`sysken-pay-admin`）の管理者パスワードを、**大学の Microsoft アカウント（Entra ID）でのログイン**に置き換える設計メモ。
この機能に関わる作業をするエージェント・人は、**実装の前にこのファイルを読み、「作るときのルール」を守ること**。
決まっていないこと（「未決事項」）を勝手に決めて実装しない。

参考にした PoC は、作者のローカルにある `ait-entra-poc`（リポジトリ外）。PoC はブラウザ側だけでログインを終えているので、このリポジトリでは**バックエンドでの検証と許可リスト**を足す。

## 決定済み

- 対象は **PC の管理サイトだけ**。ラズパイ（チャージ・管理メニュー）は今のパスワード認証のまま
- **パスワード認証は予備として残す**。管理者向けの API は「Entra のトークン」か「今の BASIC 認証」のどちらでも通る
- ログインできるのは **UPN の許可リスト**にいる人だけ。許可リストは DB に持ち、管理サイトで編集する
  - 管理サイトで学籍番号を検索 → Graph で本人を特定 → UPN を許可リストに足す
  - 最初の 1 人は、予備のパスワードで管理サイトに入って足す
- バックエンドが検証するのは **ID トークン**（`aud` は Entra のクライアント ID）
- Entra のアプリ登録は、シス研で自由に使ってよい
- ログイン中の人の**プロフィール画像**を、管理サイトの右上に出す（Graph の `/me/photo/$value`、スコープ `User.Read`。取れなければイニシャル）
- ユーザー登録の画面を**管理サイトに新設**する。学籍番号を入れると Graph で氏名を引いて登録する。ラズパイの `user-register`（名前の手入力）は残す
- **システムアカウント `sysken@aitech.ac.jp` は例外**。学籍番号と UPN の変換には混ぜず、定数として別に扱う。許可リストに**最初から入れ**（`init.sql` と migration `008`）、**外せない**（`ErrSystemAccount`、API は 409。管理サイトでも外すボタンを押せなくする）
- **ラズパイからユーザー委任（Graph）のリソースを叩かない**。Graph を呼ぶのは PC の管理サイトだけ
- JWT の検証には `github.com/golang-jwt/jwt/v5` を使う（RS256 だけ許可）。JWKS の取得とキャッシュは自前（`middleware/entra_verify.go`）
- 作業は3つの PR に分ける（上の「作る順番」）。README・docs の更新は、それぞれの feat ブランチに含めてよい

## 全体の流れ

### ログイン

1. 管理サイトで「Microsoft でログイン」→ Entra のサインイン（リダイレクト方式）
2. 管理サイトが ID トークンを `Authorization: Bearer …` で API に送る
3. バックエンドが検証する: 署名（JWKS）、`iss`（テナント固定）、`aud`、`tid`、有効期限
4. トークンの UPN（`preferred_username` を小文字にしたもの）が許可リストにあれば通す。なければ 403

### 許可リストの編集

- 管理サイトの「管理者の許可」画面で、学籍番号を検索 → 本人（氏名・UPN）を確認 → 追加
- 削除もできる。**最後の 1 人**と**自分自身**は消せない（締め出し防止）

### ユーザー登録（管理サイト）

- 学籍番号を入れる → Graph で氏名を取得して表示 → 確認して `POST /v1/user`

## 学籍番号と UPN

- 学籍番号は PoC の形式（`X24042`）が本来の形。**DB の `user.id` には先頭に `20` を付けて入れる**（`20X24042`。望ましくはないが、既存の `20K23099` の形式に合わせるため受け入れた）。変換は `aitid.UserID` / `aitid.StudentIDFromUserID`
- UPN は `小文字の学籍番号 + 学科の文字をもう1つ + @aitech.ac.jp`（例 `x24042xx@aitech.ac.jp`）

- 変換できるのは、**決めた形式に合う学籍番号だけ**。形式に合わないものは、変換せずにエラーにする
- `sysken@aitech.ac.jp` は定数 `SYSTEM_ACCOUNT_UPN` として明示する。許可リストには UPN のまま入り、学籍番号の列は空
- 変換規則は、UPN の実例を使った単体テストで固定する

## データ（DB）

- 許可リストのテーブル（migration `007`）: `upn`（主キー、小文字）、`student_id`（空でもよい）、`added_by`、`created_at`
- `init.sql` にも同じ定義を足す

## 作るときのルール（エージェントはこれを必ず守る）

1. **BASIC 認証のコードを弱めない**。Entra は足すだけで、`BasicAuth` の挙動は変えない（安全ルール4）
2. Entra の設定（`ENTRA_TENANT_ID`、`ENTRA_CLIENT_ID`）が**未設定なら、Bearer はすべて拒否**する。開けっぱなしにしない
3. 検証は署名だけで済ませない。`iss`・`aud`・`tid`・`exp`/`nbf` を必ず確かめる。`alg=none` と、RS256 以外は拒否する
4. トークンは **localStorage に置かない**。MSAL に任せる。パスワードの sessionStorage は今まで通り
5. トークン・UPN・学籍番号を**ログに出さない**（アクセスログでも）
6. **ラズパイのフロント（`sysken-pay-front`）に Graph や MSAL を入れない**
7. 許可リストの変更で、管理できる人が 0 人になってはいけない（テストで確かめる）
8. 新機能にはテストを付ける。お金に関わる API が Bearer でも同じく守られることを、`router_test.go` で確かめる
9. DB に触る前に `make backup`。migration は既存の書式に合わせる

## 受け入れているリスク

- ID トークンは本来 API に送るものではない。小さな系なので受け入れる。問題が出たら、自前 API のスコープに切り替える
- 許可リストの UPN は、アカウントの作り直しで別人になりうる。必要なら `oid` を併せて持つ（今はしない）

## 確認済み

- Graph のスコープ `User.ReadBasic.All`（委任）は、アプリ登録の画面で「管理者の同意が必要: いいえ」。使う人が最初に 1 回、同意すればよい（管理サイトの「Microsoft で名前を探す」でポップアップが出る）

## 未決事項（勝手に決めない）

- Entra のアプリ登録に必要な設定（SPA のリダイレクト URI、ID トークンの発行、`preferred_username` の任意クレーム）
- トークンの更新に iframe が要る場合の CSP（`frame-src`）
- システムアカウントでログインする人と、共有アカウントの多要素認証の扱い
