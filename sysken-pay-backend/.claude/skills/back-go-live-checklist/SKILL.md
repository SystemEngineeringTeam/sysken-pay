# Back Go-Live Checklist

バックエンドを本番に出す前の棚卸し。目的は止めることではなく、**何が起きうるかをユーザーが理解した上で判断できる状態にする**こと。お金を動かす API が誰でも叩ける・データが消える構成などを見つけたら、直るまで反映しない。

## Step 1: 公開範囲とリスクレベルを判定する

バックエンドは**部員の学籍番号・氏名と、お金（残高・購入履歴）**を持つ。この時点でリスクは「中」以上。

ユーザーに確認する（コードから分かることは聞かない）:

- API（8080）と MySQL（53306）に**どこから届くか**: ラズパイの中だけ / 部室・大学の LAN / インターネット
- 残高は実際の現金と対応しているか
- 壊れたり漏れたりしたら誰がどう困るか

| レベル | 目安 | 対応 |
|---|---|---|
| **中** | API と DB がラズパイの中（localhost）からしか届かない | Step 2〜3 を全部通し、残るリスクを明示して運用開始 |
| **高** | API や DB が LAN・インターネットから届く、または実際の現金と対応する残高を扱う | Step 2〜3 を通した上で、**運用前に詳しい人（先輩・教員など）のレビューを強く推奨する**。この推奨を省かない |

高リスクのとき「Claude のチェックだけで大丈夫」とは言わない。

## Step 2: 棚卸し

**秘密情報**
- `.env` が Git 管理に入っていないか（`git ls-files | grep -i '\.env'`）、過去の履歴にないか（`git log --all --diff-filter=A --name-only -- '*.env*'`）。見つかったらパスワードの変更を先に案内する
- `git grep -n -i -E 'password|secret|token' -- .` でハードコードがないか
- `MYSQL_ROOT_PASSWORD` が推測しやすい値でないか（値そのものはユーザーに確認してもらう。Claude は `.env` を読まない）

**認証・認可（お金を動かす API）**
- 管理系 API（ユーザー登録/更新・商品登録/更新・チャージ・購入取消・返金・利用停止）が認証の中にあるか（ルーティングは `app/server/router.go`、テストは `router_test.go`）。新しく足した API がお金や登録内容を変えるのに、`adminOnly`・`adminOrSession`・`chargeOrAdmin` のどれの中にも置かれていないことがないか。返金・ユーザーの更新や削除・許可リストの編集が、管理者バーコードの Session でも通る `adminOrSession` に入っていないか
- 本番の `.env` で `ADMIN_PASSWORD` が設定されていて、推測しにくい値か（値そのものはユーザーに確認してもらう）
- 購入（`POST /v1/user/{user_id}/purchase`）は認証なし。API に届く人は他人の学籍番号で購入できるので、API を LAN 以上に公開するなら「直してから運用すべき」に分類する
- 学生証のバーコード（学籍番号）だけで本人として購入できる。運用上許容できるか確認する

**露出面**
- CORS（`ALLOWED_ORIGINS`）が本番のフロントの配信元だけになっているか。`*` にしていないか
- `docker-compose.yaml` の `ports`: MySQL が `127.0.0.1` のままか。本番の `.env` で `API_BIND_ADDR=0.0.0.0` にしていないか（している場合は理由を確認する）
- エラー時にスタックトレースや SQL・内部エラーをそのまま返していないか（`app/ui/api/pkg/errors`）

**お金の正しさ**
- 購入・チャージなど複数テーブルを更新する処理が `transaction` を通っているか
- 負の金額・0円・極端に大きい金額を受け付けないか（domain の object と `init.sql` の CHECK 制約）
- 同じリクエストが二重に届いたときに二重に処理されないか
- これらにテスト（`*_test.go`）があるか

**データと運用**
- **MySQL のデータがボリュームに保存されているか**（`db` サービスに `mysql_data:/var/lib/mysql` がマウントされているか）。外れていたら、コンテナの作り直しでデータが消えるので**直してから運用する**
- バックアップ: `make backup` を cron で毎日回しているか（README.md の手順）、ラズパイの SD カード以外（USB メモリ等）にも保存しているか
- ラズパイの再起動後に API と DB が自動で起動するか（`restart: unless-stopped` 等）
- `Dockerfile` の Go イメージが arm64（ラズパイ 5）で動くか、`go.mod` のバージョンと合っているか
- 依存の脆弱性: `go run golang.org/x/vuln/cmd/govulncheck@latest ./...`
- テスト: `go vet ./...`、`go test ./...`
- 壊れたときに戻す手順（`back-safe-rollback` の 4-D・4-E）をユーザーが把握しているか

## Step 3: `/security-review` を実行する

反映するブランチの変更をビルトインの `/security-review` でレビューする。SQL インジェクション（`app/infra/repository`）、金額の検証漏れ、残高の同時更新を重点的に見てもらう。

## Step 4: 結果を報告し、判断を仰ぐ

「問題なし / 直してから運用すべき / 運用後でよいが対応推奨」に分けて、技術用語に一言説明を添えて報告する。

- 「直してから運用すべき」が残っている間はデプロイしない
- 「絶対に安全」とは言わない。見ていないもの（ラズパイの OS アカウント・SSH、物理的な盗難、部室ネットワークの他の機器）を一言添える
- 高リスクのときは、詳しい人のレビューの推奨を報告の冒頭に置く
- 運用開始後の最低限として「バックアップが取れているか時々確認する」「おかしいと思ったら `back-safe-rollback`」の2点を伝える

ユーザーが残リスクを理解して「運用する」と決めたら、そこで初めてデプロイ作業に進む。
