# Back Safe Rollback

バックエンドが壊れた状態から安全に戻すスキル。最優先は「元に戻すこと」ではなく「**これ以上悪化させないこと**」。

バックエンドは**部員のお金（残高・購入履歴）を持つ DB** を扱う。コードは戻せても、DB のデータを消すと取り返せない。DB に触れる操作は、コードより一段慎重に扱う。

## 大原則

1. **消さない・上書きしない。** 使ってよいのは「追加する」操作（ブランチ作成、stash、revert コミット）だけ。`git reset --hard`、`git clean`、force push、`docker compose down -v`、`docker volume rm` は使わない（deny と hook でもブロックされる）
2. **作業前に必ず退避する。** コードはバックアップブランチ、DB は `mysqldump`
3. **`docker compose down` も使わない。** 今の `docker-compose.yaml` は MySQL のデータをボリュームに保存していないので、コンテナを消すと残高データが消える（`make down` も同じ）
4. **1操作ごとに平易な言葉で説明する。**
5. **2回試して直らなかったら手を止めて**、現状・試したこと・残りの選択肢を報告する

## Step 1: 現状を凍結して把握する

```
git status
git log --oneline -15 -- .
git diff
git stash list
docker compose ps
docker compose logs --tail=100 sysken-pay
```

ユーザーに聞く:

- いつまで動いていたか / 直前に何をしたか（コード変更・ラズパイへの反映・DB 操作・`init.sql` の変更）
- どの操作で何が起きるか（API のレスポンス、エラーメッセージ）
- **お金に関わる症状か**（残高が合わない、二重に引かれた、チャージが消えた）。そうなら 4-E を最優先で読む

## Step 2: 壊れ方を分類する

| 状況 | 見分け方 | 対応 |
|---|---|---|
| 未コミットの変更で壊れた | `git status` に変更があり、最後のコミットでは動いていた | 4-A |
| コミット済み（未push） | 壊した変更がローカルのコミットにある | 4-B |
| push 済み | GitHub にも上がっている | 4-C |
| ラズパイの API が動かない | 部室の環境だけでエラー・起動しない | 4-D |
| DB・データがおかしい | 残高・商品・ユーザーが消えた・合わない | 4-E |

`go test ./...` を手がかりに、どのコミットから壊れたかを絞る（過去のコミットを見る前に Step 3 で退避する）。

## Step 3: 現状を退避する

```
git stash push -u -m "rollback前の未コミット退避 <日付>"   # 未コミット変更がある場合
git branch backup/before-rollback-<日付>
```

**DB に少しでも関わる場合は、ここで DB も退避する**:

```
docker exec sysken-db mysqldump -u root -p sysken_pay > backup-<日付>.sql
```

パスワードはユーザーに入力してもらう（Claude は `.env` を読まない）。退避できたことをファイルサイズと先頭行で確認してから先へ進む。

## Step 4: 安全な手段で復旧する

- **4-A**: `git stash push -u -m "壊れた変更の退避 <日付>"`。stash は消さない
- **4-B**: `git revert <コミット>`。複数なら `git revert --no-commit <古い方>..HEAD` してから1コミットに
- **4-C**: ローカルで revert して通常の push。revert も PR で出す

### 4-D: ラズパイの API を戻す

1. ラズパイで今のコミットを確認（`git log -1`）
2. `git switch -c rollback/<日付> <動いていたコミット>`（今のブランチは消さない）
3. `git diff <今のコミット> <動いていたコミット> -- docker-compose.yaml` で、DB コンテナが作り直される変更（`db` サービスの image・environment・volumes の変更）が無いかを確認する。**あれば実行せず手を止めて**、先に 4-E の手順で DB を退避する
4. `docker compose build sysken-pay && docker compose up -d sysken-pay`（API のコンテナだけを作り直す）
5. `curl http://localhost:8080/v1/health` 等で応答を確認

### 4-E: DB・データを戻す

1. Step 3 の DB 退避が済んでいることを確認する。済んでいなければ先にやる
2. 戻す手段（以前の dump、手での修正 SQL）があるか確認する。**どちらも無い、または削除・上書きを伴う場合は実行せず手を止めて**、状況を整理してユーザーに判断を仰ぐ
3. 残高のずれは、残高を直接書き換えず、購入・チャージの履歴と突き合わせて原因の取引を特定する。直すときは、どの行を・なぜ・どう変えるかを示して明示的な承認を得る
4. `db/init.sql` は**最初にコンテナを作るときだけ**実行される。書き換えても既存 DB は変わらない。スキーマを変えたいときに DB を作り直す（= データを消す）方向へ進まない
5. 本番 DB に `DROP` / `TRUNCATE` / 条件なしの `DELETE` / `UPDATE` を実行しない

## Step 5: 直ったことを確認する

```
go vet ./...
go test ./...
```

訴えのあった症状が実際に消えたかを、API を叩いて（`test.http` 等）確認する。お金の症状なら、該当ユーザーの残高と履歴が合っているかを確認する。

## Step 6: 平易な言葉でまとめる

- 原因（分からなければ「分からなかった」）
- 何をどこまで戻したか
- 退避した状態の場所（`backup/...` ブランチ、stash、DB の dump ファイル）
- 再発防止に次にやるとよいこと（テスト追加、DB のボリューム設定など）

退避ブランチ・stash・dump は勝手に消さない。
