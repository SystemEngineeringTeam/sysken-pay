# Back Task Intake

思いつきをそのまま issue にせず、観点を出しながらユーザーと一緒に詰めてから起票する。判断するのは常にユーザーで、Claude は考えるのを手伝う役。

**前提**: `gh` CLI がインストール・認証済み（`gh auth status`）。リポジトリは `SystemEngineeringTeam/sysken-pay`。

## Step 1: アイデアを聞く

会話の中で十分語られていれば聞き直さない。

## Step 2: 重複を確認する

`gh issue list --search "<キーワード>" --state all` で似た issue が無いか確認する。あれば、新規か既存の更新かをユーザーに確認する。

## Step 3: 観点で理解を深める

儀式的に全部聞かず、会話の中で確認する。関係ない観点は軽く流してよい。ただし**会計観点だけは特別**（後述）。

- **Engineer 観点**: どのレイヤーに手が入るか（`app/ui/api` → `app/usecase` → `app/domain` → `app/infra`）。API を変えるなら `docs/openapi.yaml` の更新と、フロントでの `pnpm generate:api`・画面側の issue が要る。DB を変えるならマイグレーションの方法（今は `init.sql` しか無く、既存 DB には効かない）を決める必要がある
- **PM 観点**: スコープは適切か（大きければ分割を提案）。フロントの作業との順番・依存
- **PO 観点**: 受け入れ条件を明確にできるか。誰（買う部員 / チャージする部員 / 管理者）にどんな価値があるか
- **運用観点**: ラズパイの本番 DB にどう反映するか。反映の前後で `mysqldump` を取る手順が要るか
- **会計観点**（お金・残高・購入履歴・チャージに関わるタスク）: 残高が正しく保たれるか

### 特別ルール: 会計観点の懸念は必ず言葉にして解消する

お金に関わる懸念が少しでも浮かんだら、他の観点がすべて問題なくても、**そのまま流さずユーザーに明示し、一緒に解消してから次へ進む**。「実装上は問題ないので起票します」で済ませない。たとえば:

- 二重送信・通信の再送で、二重に引き落とし・チャージされないか
- 途中で失敗したとき、残高と履歴の片方だけ更新されないか（`transaction` を通るか）
- 取消・返金の手段と、その記録が残るか
- 負の金額・0円・極端な金額・残高不足をどこで止めるか
- 現金箱の中身と残高の合計を後から突き合わせられるか

## Step 4: 起票内容をまとめる

- **タイトル**: `feat(back):` / `fix(back):` / `docs(back):` / `chore(back):` で始める。番号は付けない。例: `fix(back): 購入APIの二重送信で残高が二重に引かれる`
- **背景・なぜやるか**
- **受け入れ条件**（お金に関わるなら、確かめるテストケースを含める）
- **スコープ**: 含むこと / 含まないこと
- **API・DB の変更**: 変わるエンドポイント、テーブル、本番 DB への反映方法
- **実装メモ / 検討メモ**（会計観点の懸念とその解消内容は必ず残す）

## Step 5: 確認する

ドラフトを見せ、「この内容で起票する / 直す / やめる」を確認する。

## Step 6: issue を作成する

1. `gh label list` で既存ラベルを確認し、合うもの（`backend` 等）があれば使う。**無いラベルを勝手に作らない**
2. `gh issue create --title "<タイトル>" --body "<本文>"`（必要なら `--label`）
3. URL と番号を伝える。フロント側の作業も必要なら、`front-task-intake` での起票を提案する
