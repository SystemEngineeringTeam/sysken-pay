# Front Task Intake

思いつきをそのまま issue にせず、観点を出しながらユーザーと一緒に詰めてから起票する。判断するのは常にユーザーで、Claude は考えるのを手伝う役。

**前提**: `gh` CLI がインストール・認証済み（`gh auth status`）。リポジトリは `SystemEngineeringTeam/sysken-pay`。

## Step 1: アイデアを聞く

会話の中で十分語られていれば聞き直さない。

## Step 2: 重複を確認する

`gh issue list --search "<キーワード>" --state all` で似た issue が無いか確認する。あれば、新規か既存の更新かをユーザーに確認する。

## Step 3: 観点で理解を深める

儀式的に全部聞かず、会話の中で確認する。関係ない観点は軽く流してよい。ただし**画面サイズ観点だけは特別**（後述）。

- **Engineer 観点**: どのレイヤーに手が入るか（`src/docs/ARCHITECTURE.md`: adapter → services → hooks → store → pages/components）。新しい API が要るならバックエンド側の issue も必要
- **PM 観点**: スコープは適切か（大きければ分割を提案）。他の人の作業と同じページを触らないか
- **PO 観点**: 受け入れ条件を明確にできるか。誰（買う部員 / チャージする部員 / 管理者）にどんな価値があるか
- **Designer 観点**: 既存の画面の流れ（左上にタイトル、左下「戻る」、右下「次へ」、完了画面から「ホームへ戻る」）と一貫しているか。用語（「シスPay」「チャージ」等）がそろっているか
- **お金の表示観点**（購入・チャージ・残高を表示・操作する画面）: 確定ボタンの連打で二重送信されないか、エラー時に成功画面へ進まないか、金額・残高の見え方が誤解を生まないか

### 特別ルール: 800x480 に収まるかを必ず確かめる

画面に要素を足す・変えるタスクは、**5インチの 800x480 タッチ画面に収まるか、指で押せる大きさか**を必ずユーザーと確認してから起票する（`front-pi-display-ui` のルール）。「PC では収まる」で済ませない。収まらないなら、ページを分ける・項目を減らす等の案を一緒に考え、決まった内容を issue に書く。

## Step 4: 起票内容をまとめる

- **タイトル**: `feat(front):` / `fix(front):` / `docs(front):` / `chore(front):` で始める。番号は付けない。例: `fix(front): チャージ確定ボタンの連打で二重にチャージされる`
- **背景・なぜやるか**
- **受け入れ条件**（800x480 で収まることを含める）
- **スコープ**: 含むこと / 含まないこと
- **対象画面**: `src/pages/` のパス
- **実装メモ / 検討メモ**（あれば。懸念とその解消内容は残す）

## Step 5: 確認する

ドラフトを見せ、「この内容で起票する / 直す / やめる」を確認する。

## Step 6: issue を作成する

1. `gh label list` で既存ラベルを確認し、合うもの（`frontend` 等）があれば使う。**無いラベルを勝手に作らない**
2. `gh issue create --title "<タイトル>" --body "<本文>"`（必要なら `--label`）
3. URL と番号を伝える
